## Summary

This plan extends the existing Web-Based VM Management Platform with three major capabilities: (1) a **Zero-Touch Provisioning Engine** that automatically configures scoped sudoers rules on newly registered VMs — eliminating the need for any interactive sudo password handling, (2) a **Multi-Page Dashboard Architecture** replacing the current single-page modal layout with React Router-based navigation, and (3) **Advanced Telemetry** adding real-time network throughput and process explorer views to each VM's detail page.

## Detailed Architecture: Phase 10 — Zero-Touch Provisioning

### Step 1: Infrastructure Scaffolding — Provisioning Script

**File**: `backend/scripts/provisioning/setup_vm_sudoers.sh`

The script is the single source of truth for what gets installed on target VMs. It is:
- Reviewed and version-controlled alongside the Go codebase.
- Embedded at compile time (never deployed as a standalone file).
- Idempotent — safe to run multiple times on the same host.

**Script Logic**:
```
1. Accept $1 = SSH username
2. Define allowed commands:
   - /usr/bin/systemctl *
   - /usr/bin/journalctl *
3. Generate sudoers content:
   "<username> ALL=(ALL) NOPASSWD: /usr/bin/systemctl *, /usr/bin/journalctl *"
4. Write to temporary file: /tmp/vm-platform-sudoers-<username>
5. Validate with: visudo -c -f /tmp/vm-platform-sudoers-<username>
6. If validation PASSES:
   - Move to /etc/sudoers.d/vm-platform-<username>
   - Set permissions: chmod 0440
   - Set ownership: chown root:root
   - Exit 0
7. If validation FAILS:
   - Remove temporary file
   - Print error to stderr
   - Exit 1
8. Always: Remove /tmp/vm-platform-provision.sh (self-cleanup)
```

**Security Properties**:
- ✅ Scoped to `systemctl` and `journalctl` only (Constraint #4)
- ✅ `visudo -c` validates before applying (Constraint #5)
- ✅ No blanket `NOPASSWD: ALL`
- ✅ Self-cleans temporary files

### Step 2: Backend Engine — `ssh/provisioner.go`

**File**: `backend/internal/ssh/provisioner.go`

```
Package: ssh

//go:embed directive bundles scripts/provisioning/setup_vm_sudoers.sh

Exports:
  func ProvisionVM(db *sql.DB, vmID string) error
    1. Fetch VM record from DB (host, username, credentials)
    2. Update provisioning_records.status = "pending"
    3. Open SSH session via existing NewSession(db, vmID)
    4. Upload embedded script:
       - session.RunCmd("cat > /tmp/vm-platform-provision.sh << 'HEREDOC'\n" + embeddedScript + "\nHEREDOC")
    5. Execute provisioning:
       - session.RunCmd("sudo bash /tmp/vm-platform-provision.sh " + vm.Username)
    6. Check exit code:
       - If 0: Update provisioning_records.status = "provisioned"
       - If non-0: Update provisioning_records.status = "failed", store error message
    7. Log audit event: VM_PROVISIONED or VM_PROVISIONING_FAILED
    8. Return error (nil on success)
```

**Key Design Decisions**:
- Uses `//go:embed` (Constraint #3) — the script is compiled INTO the binary.
- Reuses `internal/ssh.NewSession()` — no new SSH connection logic.
- Runs asynchronously (`go ProvisionVM(...)`) after `CreateVM` returns 201.
- The `//go:embed` path is relative to the Go source file, so `provisioner.go` references `../../scripts/provisioning/setup_vm_sudoers.sh` or the embed is declared at the package level with appropriate paths.

### Step 3: API Integration — Injection into Add Server Flow

**File**: `backend/internal/api/handlers/vm.go` (modified)

The `CreateVM` handler is extended with a post-persist provisioning trigger:

```
Current flow:
  1. Decode request
  2. Encrypt credential
  3. Persist to DB
  4. Return 201

New flow:
  1. Decode request
  2. Encrypt credential
  3. Persist VM to DB
  4. Create provisioning_records entry with status "pending"
  5. Launch async: go ssh.ProvisionVM(h.DB, vm.ID)
  6. Return 201 (with provisioning_status: "pending")
```

**Why async**: Provisioning takes 5–30 seconds (SSH handshake + script execution). The API must return immediately to keep the frontend responsive. The provisioning result is polled by the frontend or observed via the inventory list's provisioning badge.

**New endpoint** `POST /api/vms/{id}/provision`:
- Triggers re-provisioning for VMs that failed or need refreshing.
- Validates the VM exists.
- Creates/updates the provisioning record.
- Launches `go ssh.ProvisionVM(...)` asynchronously.

## Explicitly Rejected Patterns

The following patterns are **permanently excluded** from this architecture per the Architectural Constraints:

| Pattern | Why Rejected |
|---------|-------------|
| `SudoPromptModal` component | Violates Constraint #1: No sudo passwords in the frontend |
| `POST /api/vms/{id}/sudo` endpoint | Violates Constraint #1: No API endpoints accepting password payloads |
| `sudo_password` field in any request body | Violates Constraint #1: No credential transmission |
| `SudoSessionCache` entity | Unnecessary — no passwords exist to cache |
| Frontend `localStorage` sudo token | Violates Constraint #1: No credential storage in browser |
| Runtime-loaded provisioning script | Violates Constraint #3: Script must be embedded at build time |
| `NOPASSWD: ALL` sudoers rule | Violates Constraint #4: Rules must be command-scoped |
